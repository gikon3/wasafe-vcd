# wasafe-vcd

Чтение и запись VCD (IEEE 1364) для ядра [wasafe](../wasafe): `VcdReader` наполняет
любой `Builder`, `VcdWriter` выгружает любую `Database`. Чтение и запись — горячий
путь: собственный буфер вместо `iostream`, `std::from_chars`/`std::to_chars`, память
не зависит от размера дампа.

- Спеки и планы — `docs/superpowers/specs/`, `docs/superpowers/plans/`, правила — в
  разделе «Спеки и планы».
- `docs/backlog.md` — дефекты и пожелания из проектов, которые используют
  библиотеку (сейчас — Phosphor). Пункт берётся в работу как задача; закрытый пункт
  удаляется из файла в том же коммите, что и исправление.

## Сборка и тесты

```bash
.venv/bin/conan install . --build=missing -s compiler.cppstd=23 -s build_type=Debug
cmake --preset conan-debug
cmake --build --preset conan-debug
ctest --preset conan-debug --output-on-failure
```

- wasafe и wasafe-vcd — editable-пакеты Conan (`../wasafe`, этот каталог): изменение
  здесь сразу видно Phosphor, а изменение в `../wasafe` — здесь. `../wasafe` — отдельный
  репозиторий со своими правилами; нужная там доработка записывается в его
  `docs/backlog.md`, коммитит там пользователь.
- Профили: `conan-release` (`-s build_type=Release`), `conan-debug-asan-ubsan`
  (`-pr:a .github/conan/asan-ubsan`). Бенчмарк — `-DWASAFE_VCD_BUILD_BENCHMARKS=ON`,
  бинарь `wasafe-vcd-bench`; изменения горячего пути чтения и записи проверяются им
  в Release.
- Тесты — один бинарь `wasafe-vcd-tests`; файлы перечисляются в
  `tests/CMakeLists.txt` явно, без `file(GLOB)`.
- CI собирает под clang с ASan+UBSan, clang Release, GCC, MSVC и big-endian s390x под
  qemu, плюс clang-format и clang-tidy по всему дереву. Код, который раскладывает
  биты и байты, не должен зависеть от порядка байт хоста.

## Код

- C++23, пространство имён `WaSafe::Vcd`; публичные заголовки — `include/wasafe_vcd/`,
  внутренние — `src/`. Файлы `snake_case`, методы `camelCase`, закрытые поля с
  суффиксом `_`.
- Ошибки — исключением `WaSafe::Vcd::Error` (`throw Error{"..."}`); префикс `vcd: `
  добавляет конструктор, в тексте его не повторять.
- Форматирование — `.clang-format`, проверки — `.clang-tidy`; изменённые файлы
  форматируются хуком после каждой правки. Перед тем как показывать результат:

  ```bash
  .claude/scripts/clang-format.sh --check
  .claude/scripts/clang-tidy.sh -p build/Debug
  ```

  Без аргументов скрипты берут файлы, изменённые относительно HEAD; заголовок
  проверяется через `.cpp`, которые его включают. Ожидаемый итог — «формат чист» и
  «замечаний нет».
- Однострочное тело `if`/`else`/`while`/`for` — без фигурных скобок; в цепочке
  `if / else if / else` скобки либо у всех веток, либо ни у одной.
- Вызов конструктора класса — фигурными скобками вместо круглых, где это возможно
  (`VcdReader reader{path}`, `: out_{path}` в списке инициализации). Скаляры,
  константы и `auto` инициализируются присваиванием (`const auto got = f();`).
- В новом коде вместо «bool + out-параметр» — `std::optional<T>`.
- Строковые литералы в коде — на английском, без кириллицы (сообщения исключений,
  вывод бенчмарка).
- Комментарии на русском, по общим правилам из `~/.claude/CLAUDE.md`.

## Спеки и планы

- Имена файлов: `ГГГГ-ММ-ДД-<тема>-design.md` в `specs/`, `ГГГГ-ММ-ДД-<тема>-plan.md`
  в `plans/`.
- Шапка спеки: дата, статус («черновик на согласование» или «согласовано») и строка
  «Обновлено: …» на каждую правку после согласования. Выбор, который автор спеки
  сделал сам, не обсудив его с пользователем, помечается **[решение спеки]**: так
  видно, что ещё можно оспорить.
- Спека разделяет цели, не-цели и анти-цели. У не-цели сказано, какое ограничение
  она накладывает на архитектуру уже сейчас. Постоянная анти-цель библиотеки —
  замедление горячего пути и память, которая растёт с размером дампа.
- Шапка плана: цель, архитектура, ссылка на спеку и раздел **Global Constraints** —
  выдержка из этого файла, которая касается плана, ветка работы и команды сборки и
  тестов. Исполнителю задачи план должен хватать без чтения остального репозитория.
- Следом — **Review Focus**: 3–5 самых рискованных граничных случаев (обрыв файла,
  пустой дамп, предельные размеры, порядок байт) и номер задачи, тест которой
  каждый из них закрывает.
- Задача плана выполняется по TDD: сначала тест и его падение (RED), потом
  реализация (GREEN).
- Рабочие файлы субагентной разработки (`.superpowers/`) в git не попадают.

## Работа по плану и коммиты

- Коммиты делает пользователь. `git add`, `git commit`, `git push` — только по явной
  просьбе на конкретный коммит.
- После каждого пункта плана (а не всего плана) остановиться: прогнать сборку, тесты,
  clang-format и clang-tidy, честно привести результат, включая падения, кратко
  показать сделанное и предложить сообщение коммита в блоке кода. Следующий пункт —
  только после ответа пользователя. Если пункт слишком мелкий для отдельного коммита,
  всё равно остановиться и сказать об этом.
- Агенты-исполнители задач не коммитят и не меняют ветку.
- Ветки `feat/…`, `fix/…` можно заводить без спроса; в `main` напрямую не работать.
- Сообщение коммита: префикс, двоеточие, коротко по-русски без точки в конце.
  Префиксы: `add:` (новое), `fix:` (исправление ошибки или предупреждений), `mod:`
  (изменение поведения), `refactor:` (без изменения поведения), `build:` (сборка,
  зависимости, CI), `doc:` (документация). Тело — только если нужно объяснить «почему».
