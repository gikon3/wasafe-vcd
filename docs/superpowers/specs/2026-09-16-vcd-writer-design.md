# Дизайн: VcdWriter — экспорт Database в текстовый VCD

Дата: 2026-09-16
Обновлено: 2026-09-24 — Emitter пишет через временный файл с атомарной заменой
целевого (§3.1, §5); ошибки модуля — `Vcd::Error` (§5).

## 1. Задача и цель

`VcdWriter::write()` сегодня — заглушка, бросающая `"VCD writer not implemented"`.
Нужен полноценный экспорт `Database` обратно в текстовый VCD (IEEE 1364).

Writer проектируется как **первоклассный горячий путь, симметричный `VcdReader`**:
у него собственный буфер вывода вместо `ostream`, форматирование через `to_chars`,
пакетная упаковка бит в символы и потребление памяти, не зависящее от размера
дампа. Это зеркало того, что уже сделано на чтении в `Scanner` и `ValueBuffer`.

### Известный дефект, который чинится попутно

`src/writer.cpp` в текущем виде **не компилируется**: libstdc++ 16 намеренно
объявляет `std::formatter<std::filesystem::path>` с удалённым конструктором
копирования, поэтому `std::format("vcd: failed to open file {}", path)` даёт
ошибку компиляции. Цель `wasafe_vcd` сейчас собирается только из устаревших
объектных файлов. Правильная форма уже есть в конструкторе `Scanner`
(`src/scanner.cpp`) — конкатенация с `path.string()`.

Там же: `std::fstream file{path}` без флагов открывается как `in|out` и не
создаёт несуществующий файл, а `std::endl` сбрасывает поток на каждой строке.
Ни одна из трёх строк текущей заглушки в итоговый код не переходит.

## 2. Границы

**В объёме.** Полный экспорт всей БД: `$version`, `$timescale`, `$scope`/`$upscope`,
`$var`, `$enddefinitions`, поток меток времени и изменений значений. Виды значений:
logic (скаляры и векторы), real, string. Алиасы (несколько `$var` на один поток).
Развёртка композитов в плоские `$var` с индексированными именами.

**Вне объёма (сознательный YAGNI).** Опции writer'а (свои `$date`/`$version`,
точность печати real, размер буфера) — интерфейс остаётся ровно
`Writer::write(const Database&, const std::filesystem::path&)`. Выборочный
экспорт (диапазон времени, поддерево scope). Секции `$dumpoff`/`$dumpon`,
`$comment`. Бинарные форматы.

## 3. Архитектура

Три новые единицы плюс дополнение существующей, зеркально reader'у:

| Чтение | Запись | Роль |
| --- | --- | --- |
| `Scanner` (`scanner.hpp/.cpp`) | `Emitter` (`emitter.hpp/.cpp`) | единственная точка работы с файлом, свой буфер |
| `ValueBuffer` (`value_buffer.hpp`) | `value_text.hpp` | преобразование бит-планов ↔ текст |
| `CodeTable` (`code_table.hpp`) | `CodeBook` (`code_book.hpp`) | соответствие «поток ↔ код VCD» |
| `Parser` (в `reader.cpp`) | `Dumper` (в `writer.cpp`) | обход и протокол формата |
| `vcd_syntax.hpp/.cpp` | он же, дополняется | лексика формата, чистые функции |

`Dumper`, как и `Parser`, живёт в анонимном namespace своей единицы трансляции и
создаётся заново на каждый вызов `write()` — состояние заведомо чистое.

### 3.1. Emitter — слой вывода

Ключевое решение — **форма API**. Не набор `write(...)`-методов с проверкой на
каждый вызов, а резервирование: `reserve(n)` возвращает сырой указатель на `n`
гарантированно свободных байт, вызывающая сторона заполняет их без единой
проверки границ и подтверждает фактически записанное через `commit()`.

У каждой записи VCD есть вычислимая верхняя оценка длины, поэтому `Dumper`
делает **один** `reserve()` на изменение значения и дальше работает указателем —
ровно так же, как `Scanner::next()` работает указателем внутри уже прочитанного
блока. Альтернатива с посимвольными `text()`/`ch()` стоила бы ветвления на
символ, а символов здесь сотни миллионов.

```cpp
/// Потоковый вывод текстового VCD: собственный буфер поверх ofstream без его
/// буферизации, запись через временный файл с атомарной заменой целевого.
/// Зеркало Scanner — там блок читается, здесь пишется.
class Emitter final {
public:
    explicit Emitter(std::filesystem::path path, std::size_t bufferSize = kDefaultBufferSize);
    Emitter(const Emitter&) = delete;
    Emitter(Emitter&&) = delete;
    /// Если finish() не завершился успешно — закрывает поток и удаляет
    /// временный файл; целевой не трогает. Не бросает.
    ~Emitter();

    /// n гарантированно свободных байт. Быстрый путь инлайнится намеренно:
    /// межмодульного инлайнинга в сборке без LTO нет.
    [[nodiscard]] char* reserve(std::size_t n) {
        if (pos_ + n > buf_.size())
            flushFor(n);
        return buf_.data() + pos_;
    }

    /// Подтвердить фактически записанное; end — конец заполненного участка.
    void commit(const char* end) { pos_ = static_cast<std::size_t>(end - buf_.data()); }

    /// Удобная обёртка для заголовка, где горячего пути нет.
    void text(std::string_view s);

    /// Дописать остаток, закрыть временный файл и атомарно заменить им целевой.
    /// Единственное место, где ошибка записи превращается в исключение на
    /// успешном пути.
    void finish();

    Emitter& operator=(const Emitter&) = delete;
    Emitter& operator=(Emitter&&) = delete;

public:
    static constexpr std::size_t kDefaultBufferSize = std::size_t{1} << 20U;

private:
    /// Сбросить буфер в файл; если n не влезает даже в пустой — вырастить его.
    void flushFor(std::size_t n);

private:
    std::filesystem::path path_;     ///< целевой файл
    std::filesystem::path tmpPath_;  ///< `<path>.<pid>.tmp`, строится из path_
    std::ofstream out_;
    std::vector<char> buf_;
    std::size_t pos_ = 0;
    bool committed_ = false;  ///< finish() успешно заменил целевой файл
};
```

#### Временный файл и атомарная замена

Emitter пишет не в целевой файл, а в соседний временный `<path>.<pid>.tmp`, и
только `finish()` подменяет им целевой через `std::filesystem::rename`. Ошибка
посреди выгрузки не оставляет на месте целевого файла обрезанный VCD, а прежнее
содержимое, если оно было, остаётся целым. Данные при этом не копируются:
`rename` в пределах одной файловой системы меняет только запись каталога и на
POSIX атомарен — читатель видит либо старый файл, либо новый, но не половину.

- Временный файл лежит **в том же каталоге**, что и целевой, а не в
  `temp_directory_path()`: между файловыми системами `rename` не переносит файл,
  а завершается с `EXDEV`.
- PID в имени разводит процессы, пишущие в один путь одновременно. Два `Emitter`
  на один путь внутри одного процесса не поддерживаются: у них совпадёт
  временный файл.
- Точка фиксации — только `finish()`; **деструктор никогда не публикует файл**.
  Если до успешного `finish()` дело не дошло — исключение в `Dumper`, сбой
  записи, `close()` или `rename()`, — деструктор закрывает поток и удаляет
  временный файл. Флаг `committed_` отличает эти пути от успешного; проверка
  `is_open()` для этого не годится, потому что после неудачного `rename()` поток
  уже закрыт, а временный файл ещё лежит.
- Защита рассчитана на исключения, а не на отключение питания: `fsync` перед
  `rename` не делается, и после аварии ОС целевой файл может оказаться пустым.
  Для дампов это принято сознательно.

PID берётся через `getpid()` на POSIX и `GetCurrentProcessId()` на Windows
(`<windows.h>` с `WIN32_LEAN_AND_MEAN` и `NOMINMAX`). CRT-функция `_getpid` не
используется: Microsoft помечает её устаревшей для UWP.

Временный файл открывается с `std::ios::binary | std::ios::trunc`. `binary`
обязателен, чтобы вывод был побайтово детерминирован на любой платформе. Буфер
потока отключается через `out_.rdbuf()->pubsetbuf(nullptr, 0)`: собственная
буферизация делает его лишней перекладкой памяти. Делается это **строго до
`open()`**: на уже открытом файле libstdc++ молча игнорирует `pubsetbuf` —
вызов возвращает `this` и выглядит принятым, — и поток продолжает буферизовать
сам. Поэтому файл не открывается в списке инициализации; так же устроен
конструктор `Scanner`.

Ошибки записи проверяются в `flushFor()` и `finish()` — как в
`IndexingBuilder::writeRaw()`, где запись в файл тоже собрана в одну точку.

### 3.2. Форматирование чисел

Числа пишутся через `std::to_chars` прямо в зарезервированный участок. Это не
только про локаль: `ostream` по умолчанию печатает 6 значащих цифр, из-за чего
`tests/vcd_gen.hpp` пришлось подбирать значения, «которые точно печатаются с
точностью потока по умолчанию». `to_chars` даёт кратчайшее представление с
гарантией round-trip, и эта оговорка становится не нужна.

Верхние оценки длины: 20 байт на `TimeStamp` (знаковый 64-битный),
32 байта на `double` — с запасом от `max_digits10` плюс знак, точка и экспонента.

### 3.3. value_text.hpp — бит-планы в текст

Зеркало `ValueBuffer::decode()`. Свободная функция, инлайн в заголовке:

```cpp
/// Записать вектор как текст VCD (старший разряд слева) в dst.
/// @return конец записанного.
[[nodiscard]] inline char* encodeLogic(char* dst, LogicVectorView v);
```

`LogicVectorView::toString()` для этого не годится: он аллоцирует `std::string`
на каждый вызов и набивает её посимвольно через `operator[]`, где на каждый бит
приходится проверка границ и деление на ширину слова.

Быстрый путь опирается на то же свойство, что и чтение: `bval()` возвращает
пустой span, когда значение двухзначное, — и тогда весь вектор идёт без разбора
неопределённых состояний. Слово `aval` разворачивается по восемь символов за
раз размножением байта и маской — операция, обратная `packTwoStateChunk()`.
Слова с выставленными b-битами идут по одному биту через
`toChar(logicFromAb(...))`.

**Порядок реализации:** сначала честный побитовый цикл, пакетная развёртка — по
результатам бенчмарка (см. §6). Структура кода от этого не меняется, а точная
константа размножения бит закрывается отдельным юнит-тестом.

### 3.4. Усечение векторных литералов

Основание — нормативное правило IEEE 1364 о чтении неполного вектора: «If not all
of the bits are given in a VCD vector value change, then the value is
left-extended in an unsigned fashion. Additionally, if the leftmost bit in the
unsigned number is an x or a z, then an x or a z shall be used to pad to the
left, respectively». Именно его реализует `extensionLogic()` в `value_buffer.hpp`.

Стандарт описывает, как **читать** короткое значение, и тем самым разрешает его
коротким **писать**; обязанности усекать он на писателя не накладывает. Усечение —
оптимизация размера, обратимость которой гарантирована приведённым правилом.

Пусть `c` — старший символ значения, а ведущая серия из `c` имеет длину `k`.
Правило записи распадается на четыре случая, и они **не сводятся** к «схлопнуть
серию в один символ»:

- `c == '1'` — усечения нет, вектор пишется полной ширины: расширение дополняет
  нулями, а не единицами.
- `c == 'x'` или `c == 'z'` — серия схлопывается ровно в **один** символ, а не
  отбрасывается: именно он задаёт, чем расширять, и без него значение
  дополнилось бы нулями.
- `c == '0'`, а следующий за серией символ — `'1'` — нули отбрасываются
  **целиком**: расширение восстановит их само.
- `c == '0'`, а следующий за серией символ — `'x'` или `'z'` — ровно один ноль
  обязан уцелеть. Отбросив всю серию, мы сделали бы старшим символом `x`/`z`, и
  расширение дополнило бы значение иксами вместо нулей.

Значение из одних нулей вырождается в один символ `0`.

Последний случай — единственный неочевидный, и именно он отличает это правило от
наивного «срезать всё до первой единицы», как сделано в `VcdGen::vectorLiteral()`:
там генератор строит векторы только из `0`/`1`, поэтому проблема не возникает.

### 3.5. CodeBook — коды VCD

Коды выдаются последовательностью в алфавите печатных ASCII 33..126, как их
порождают реальные симуляторы, — та же схема, что в `VcdGen::code()`.

Код выдаётся **на поток (`SignalId`), а не на узел**. Это принципиально:
несколько узлов иерархии законно делят один поток (алиасы VCD), и если отдать
их все в курсор, каждое изменение придёт дважды — по разу на `source`. Поэтому
`$var` пишется на узел, а код и место в курсоре — на поток.

`CodeBook` хранит коды в плоской арене символов и отдаёт их двумя способами:

- по `SignalId` — нужен один раз на `$var`, чтобы алиас получил код первого
  объявления. Внутри — `std::vector<std::int32_t>`, индексируемый `SignalId::get()`
  (идентификаторы потоков выдаются builder'ами подряд; при разреженности платим
  только памятью под максимальный id);
- по **порядковому номеру потока** — горячий путь. Курсор отдаёт `source` как
  индекс в переданном span'е потоков, поэтому поиск вырождается в обращение к
  массиву: ни хеша, ни сравнения строк.

### 3.6. Dumper — обход и протокол

Один проход по иерархии строит и заголовок, и всё, что нужно потоку значений.
Отдельный вызов `Database::leafNodes()` не используется намеренно: он вернул бы
и узлы-алиасы, которые всё равно пришлось бы дедуплицировать, а заголовочный
обход решает эту задачу в том же месте, где выдаёт коды.

Результат обхода: строки `$var` в выходном буфере, заполненный `CodeBook` и два
параллельных массива на **уникальные** потоки в порядке первого появления —
`SignalId` и ширина. Коды в этот набор не входят: ими по тому же порядковому
номеру заведует сам `CodeBook`. Ширина нужна, чтобы форматирование изменения не
лезло обратно в иерархию; это размер из `$var` (§4.3), а не `bitWidth()` типа,
поэтому выбор между скалярной и векторной формой совпадает с объявлением.

Массива видов значений нет: вид берётся из самого изменения, и эта проверка
нужна в любом случае — значения вида `ValueKind::NONE` пропускаются (§4.4).

## 4. Формат выходного файла

### 4.1. Заголовок

```text
$version wasafe-vcd <версия> $end
$timescale <масштаб> $end
```

`$date` **не пишется**. БД его не хранит, а подстановка текущего времени сделала
бы вывод недетерминированным и закрыла бы возможность побайтовых тестов. Reader
обе секции всё равно пропускает до `$end`. Версия берётся из
`WaSafe::Vcd::Version::kString` (генерируемый `wasafe_vcd/version.hpp`),
масштаб — из `db.timeScale()` через готовый
`WaSafe::formatTimeScale()`; его вывод («1 ps») разбирается обратно, потому что
`Parser::parseTimescaleCmd()` склеивает токены секции перед разбором.

### 4.2. Иерархия

Обход в глубину от `db.root()`. Сам корень — `ScopeKind::ROOT`, и `$scope` для
него не пишется: в VCD корневого уровня нет, его дочерние scope становятся
верхним уровнем файла. Сигналы, лежащие непосредственно в корне, пишутся
`$var`'ами до первого `$scope`; наш reader это принимает (у `VarRegistry` есть
корневой уровень), синтетический scope ради них не заводится.

Внутри scope сначала идут `$var` своих сигналов, затем вложенные `$scope`,
затем `$upscope $end`.

Отображение `ScopeKind` в ключевое слово VCD — обратное к `Vcd::scopeKind()`:
`MODULE → module`, `TASK → task`, `FUNCTION → function`, `BLOCK → begin`. Все
остальные виды (`INTERFACE`, `PACKAGE`, `PROGRAM`, `GENERATE_BLOCK`, `STRUCT`,
`UNION`, `ARRAY`, `CLASS`, `UNKNOWN`) пишутся как `module`: других слов в
формате нет, и round-trip для них лоссовый. Это ограничение VCD, а не решение.

### 4.3. Объявление переменной

```text
$var <тип> <размер> <код> <ссылка> $end
```

Узел получает `$var` тогда и только тогда, когда у него есть собственный поток
(`Signal::streamId()`); композит без потока не объявляется, обход спускается
в его `children()`. Это ровно та же граница «листа», что у
`Database::leafNodes()`.

- **тип**: `real` для `TypeKind::REAL` (`shortreal`, если `RealType` короткий),
  `string` для `STRING`, `event` для `EVENT`, во всех прочих случаях `wire`. Исходное слово (`wire`/`reg`/...)
  модель не хранит, поэтому восстановить его нельзя.
- **размер**: `type->bitWidth()` для logic-типов, `64` для real (сложившаяся
  конвенция, её же использует `tests/vcd_gen.hpp`), `32` для shortreal, `1` для
  string и event.
- **ссылка**: локальные имена узлов-предков, склеенные от верхнего уровня scope
  вниз (`mem[3]`, `hdr.addr`), плюс `[msb:lsb]` из `VectorType` (у enum — из его
  базового вектора), если ширина больше единицы. `Signal::name()` даёт только локальное имя (`[3]`), а
  `fullPath()` тянет и путь по scope, который уже выражен вложенностью `$scope`.

Комбинация индексов и диапазона (`mem[3][7:0]`) разбирается обратно корректно:
`parseReference()` принимает как диапазон только самую правую группу, а левее
собирает одиночные индексы.

**Packed-композит со своим потоком** (packed-структура) пишется одним `$var`
шириной `bitWidth()`; его члены — битовые срезы того же потока, отдельных `$var`
у них нет. На round-trip структура становится вектором. Это ограничение VCD.

**Алиасы**: второй и последующие узлы того же потока получают собственный `$var`
с тем же кодом. Reader это принимает — `CodeTable::add()` игнорирует повторную
регистрацию, оставляя поток за первым объявлением.

Заканчивается заголовок строкой `$enddefinitions $end`.

### 4.4. Поток значений

`$dumpvars` не пишется. Начальные значения при разборе исходного дампа приходят
обычными изменениями на первой метке времени, поэтому курсор воспроизводит их
сам; отдельная секция потребовала бы точечных `valueAt()` по всем потокам, что
для ленивого хранилища означает лишние подъёмы блоков.

Источник — `db.storage().openCursor(streams, kWholeTime)`: один курсор,
сливающий все потоки в общий хронологический порядок, где `source` — индекс в
переданном span'е. Память при этом не зависит от размера дампа.

Цикл: при смене метки времени пишется `#<время>`, затем изменение в форме,
которую задаёт вид значения:

| Вид | Форма | Оценка длины для `reserve()` |
| --- | --- | --- |
| logic, ширина 1 | `<0\|1\|x\|z><код>` | `1 + len(код) + 1` |
| logic, ширина > 1 | `b<биты> <код>` | `1 + width + 1 + len(код) + 1` |
| real | `r<число> <код>` | `1 + 32 + 1 + len(код) + 1` |
| string | `s<текст> <код>` | `1 + len(текст) + 1 + len(код) + 1` |

Значения вида `ValueKind::NONE` пропускаются.

**Известное ограничение:** в VCD нет экранирования, поэтому строковое значение с
пробелом или переводом строки сломает файл. Значение пишется как есть; проверка
и политика экранирования — за рамками этой спеки.

## 5. Обработка ошибок

Все ошибки модуля — `WaSafe::Vcd::Error` из публичного
`include/wasafe_vcd/exception.hpp`, наследник `WaSafe::Exception`. Конструктор
сам добавляет к сообщению префикс `vcd: `, поэтому в местах броска его не пишут.
Код, ловящий `WaSafe::Exception`, продолжает ловить и эти ошибки.

- **Имя отличается от базового намеренно.** Одноимённый `Vcd::Exception` внутри
  `namespace WaSafe::Vcd` скрыл бы базовый класс, и смысл неквалифицированного
  `throw Exception{...}` зависел бы от набора include: подключись заголовок
  транзитивно — сообщения молча стали бы `vcd: vcd: ...`. С отдельным именем
  забытый include — ошибка компиляции.
- **Класс помечен `WASAFE_VCD_API`**, как и базовый (`WASAFE_API`). Исключение
  пересекает границу библиотеки, и в shared-сборке с `-fvisibility=hidden` без
  экспорта typeinfo у клиента не совпал бы с библиотечным — `catch` по типу не
  сработал бы.

Ошибки `Emitter`:

- Файл не открылся → `Error{"cannot open " + path.string()}`. В сообщении —
  путь пользователя, а не временного файла. `std::format` с
  `std::filesystem::path` не используется (см. §1).
- Ошибка записи или `close()` → `Error{"write failed: " + path.string()}` из
  `flushFor()` или `finish()`.
- Не удалась замена целевого файла →
  `Error{"cannot replace " + path.string() + ": " + ec.message()}`. `rename`
  вызывается с `std::error_code`, чтобы наружу не вышел
  `std::filesystem::filesystem_error`.
- Деструктор `Emitter` не бросает и ничего не публикует: если `finish()` не
  завершился успешно, он закрывает поток и удаляет временный файл (§3.1).
  `close()` без маски исключений и `remove(path, ec)` не бросают, поэтому
  `try`/`catch` в деструкторе не нужен. На успешном пути `write()` всегда
  вызывает `finish()` до возврата.

## 6. Тестирование

Новый `tests/test_emitter.cpp` (зеркало `test_scanner.cpp`):

1. `SurvivesChunkBoundaries` — записи, пересекающие границу буфера, при
   размерах буфера от 1 байта; файл сверяется со склейкой записей целиком,
   чтобы был виден и лишний хвост.
2. `AppendsSuccessiveTextWrites` — соседние вызовы `text()` склеиваются встык.
3. `GrowsBufferForOversizedRecord` — `reserve()` больше всего буфера.
4. `FlushesAndClosesOnFinish` — данные на диске сразу после `finish()`, пока
   `Emitter` ещё жив.
5. `ReportsUnopenablePath` — неоткрываемый путь даёт `Vcd::Error`.
6. `KeepsOldFileWhenNotFinished` — без `finish()` прежний целевой файл цел, а
   временного не остаётся.
7. `ReportsFailedReplace` — неудачный `rename` даёт `Vcd::Error`, а не
   `filesystem_error`, и временного файла не остаётся.

Тесты с временными файлами работают в собственном каталоге и проверяют его
содержимое после разрушения `Emitter`: уборка происходит в деструкторе, а
хвосты других прогонов в общем `temp_directory_path()` не должны влиять на
результат.

Сверка содержимого не ловит выход за зарезервированный участок: байт, записанный
за `size()` буфера, при сбросе читается оттуда же, и файл выглядит верным. Такие
ошибки видит только санитайзер, поэтому тесты `Emitter` обязаны проходить и в
ASan-профиле conan.

Туда же попадают тесты `encodeLogic()` из `value_text.hpp` — на скалярах, широких
векторах и значениях с `x`/`z`. Когда появится пакетная развёртка (шаг 6 в §7),
рядом встаёт сверка быстрого пути с побитовым эталоном на случайных векторах:
именно она закрывает константу размножения бит.

Новый `tests/test_vcd_writer.cpp`:

1. `RoundTripsHierarchyAndValues` — существующий `kVcd` → ingest → write →
   ingest → сверка иерархии и значений.
2. `WritesScalarsVectorsRealsAndStrings` — все четыре формы записи.
3. `SharesOneCodeBetweenAliases` — два `$var` с одним кодом.
4. `FlattensArraysIntoIndexedNames` — `mem[3]` на выходе и обратное слияние в
   массив при повторном чтении.
5. `TrimsLeadingRunsButKeepsOnes` — правило усечения из §3.4 во всех четырёх
   случаях: ведущие нули перед единицей (отбрасываются целиком), ведущие нули
   перед `x`/`z` (один ноль обязан уцелеть), ведущие `x`/`z` (схлопываются в
   один символ) и ведущая единица (усечения нет). Плюс вырожденные значения:
   все нули, все иксы.
6. `WritesRealsIndependentlyOfLocale` — зеркало существующего теста на чтение.

## 7. Порядок реализации

1. `Emitter` и его тесты.
2. `CodeBook`, обход иерархии, заголовок и `$var`.
3. Поток значений с простым побитовым кодировщиком.
4. Round-trip тесты, включая объёмный.
5. `--stage=write` в бенчмарке.
6. Пакетная развёртка бит — только если замер покажет, что она окупается.

Шаги 1–4 дают рабочий writer; 5–6 доводят его до заявленной симметрии с reader'ом
по скорости.
